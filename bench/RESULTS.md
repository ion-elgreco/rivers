# rivers vs Dagster vs Prefect

Generated by `bench/run.sh`. Do not hand-edit — rerun it instead.

**Machine:** Darwin 25.5.0 on arm64, 16 cores, 128.0 GB RAM
**Versions:** rivers 0.0.0.dev0, Dagster 1.13.22, Prefect 3.8.5, CPython 3.13.2

Read `bench/README.md` for the method and the fairness rules
before quoting any number here. Two of them matter most:

- The sensor benchmark holds every framework to the **same** interval. Dagster's
  30-second default is a setting, not a speed limit, and comparing against it
  would produce a meaningless multiplier.
- `starved` is not a crash. The daemon keeps running and reports itself healthy
  while some sensors stop firing on time. That is the failure mode to watch for.

- **rivers:** Control plane: operator, UI, SurrealDB, plus a SurrealDB user bootstrap job.
- **rivers:** Code location is a CodeLocation resource the operator reconciles.
- **Dagster:** Control plane: webserver, daemon, PostgreSQL, plus one user-code gRPC server.
- **Dagster:** The code location installs with the chart, so it is inside control_plane_ready.
- **Dagster:** Images rebuilt natively for arm64 — Dagster publishes amd64 only.
- **Dagster:** Code location holds 10 assets.
- **Prefect:** Control plane: Prefect server plus PostgreSQL.
- **Prefect:** A worker is installed separately; the server alone cannot run a flow.
- **Prefect:** Prefect has no code location object; flows reach workers through deployments.

## Parallel execution — wall clock for the same sleeping work

Each asset sleeps 50 ms and four run at once, so the work itself needs
the same time everywhere. All three run the work in separate processes,
so all three pay pickling and process start rather than one of them
getting threads for free.

One difference is left standing and cannot be closed: rivers and Prefect
reuse a pool of four worker processes, while Dagster's
`multiprocess_executor` starts a fresh process for every step. Dagster
ships no pooled executor, so that is a property of its architecture and
not a setting left untuned. Most of Dagster's figure below is process
start, not scheduling.


| Assets | rivers | Dagster | Prefect |
|---:|---:|---:|---:|

## Log capture — write this many lines and read them back, milliseconds

The run is launched rather than executed inline, because Dagster
persists step output only for a launched run. Prefect ships logs
asynchronously, so its figure includes waiting for the lines to become
readable.

These are three different jobs, not one job measured three times.
rivers and Dagster capture the step's stdout as a stream and store it
whole. Prefect has no stream capture: it writes one structured log
record per line and ships each to its API, which is the larger reason
for its figure at 100,000 lines.
